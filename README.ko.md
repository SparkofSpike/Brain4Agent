# Brain4Agent

[English](README.md) | [简体中文](README.zh-CN.md) | [日本語](README.ja.md) | **한국어**

에이전트를 위한 장기 기억. CJK 우선 검색, 코어 경로에 모델 없음,
신뢰도 점수 대신 증거.

`pip install "Brain4Agent[precise]"`는 Python 3.11 이상과 선택적 사전 하나를
요구합니다. 그것이 없어도 모든 것은 그대로 동작합니다.

## 무엇인가

코드베이스에서 일하는 에이전트는 맥락을 쌓습니다. 어떤 결정을 왜 내렸는지,
어떤 접근이 실패했는지, 배포 환경이 어디에 있는지 같은 것들입니다. 그 맥락은
그것이 나온 대화보다 오래 살아남고, 다시 도출하는 데는 비용이 많이 듭니다.

Brain4Agent는 그런 턴들을 SQLite 파일 하나에 저장하고 세션 단위로 검색합니다.
네 가지 제약을 중심으로 설계했습니다.

- **CJK는 별도 설정 없이 동작합니다.** 한자, 가나, 한글을 공백이나 비단어
  경계로 나누면 질의가 토큰 하나로 뭉개지고, 반각 가타카나는 CJK 범위에도
  ASCII 단어 클래스에도 걸리지 않습니다. 문자 바이그램은 그런 식으로 실패하지
  않습니다. 측정값은 중국어 기준이며(벤치마크 참고), 일본어·한국어·베트남어는
  지원하고 테스트하지만 벤치마크하지는 않았습니다. README는 그 점을 얼버무리지
  않습니다.
- **코어는 모델을 호출하지 않습니다.** 검색은 BM25입니다. API 키도, 가속기도,
  콜드 스타트도 없고 질의당 한 자릿수 밀리초가 걸립니다.
- **판정이 아니라 증거를 돌려줍니다.** 검색은 신뢰도 점수 대신 질문에 있으면서
  코퍼스에는 한 번도 없었던 단어가 무엇인지 알려줍니다. 그 의미를 해석하는 일은
  이미 모델을 가진 호출자에게 맡깁니다.
- **저장되는 것과 인덱싱되는 것은 다릅니다.** 기억은 사람이나 리더가 읽을 전체
  텍스트를 보관하고, 인덱스는 더 좁고 더 특징적인 것을 담을 수 있습니다. 둘을
  분리하는 것만으로 PrecisionMemBench가 0.6104에서 0.7922로 올랐습니다. 설명하는
  산문은 평범한 단어를 도메인 전체와 공유하기 때문에 특징적인 이름 하나보다 위로
  올라오기 때문입니다.

기억에는 `tags`(범위), `superseded_by`(대체), `refs`(한 홉 링크)도 붙습니다.
어느 것도 추론하지 않고 모델도 필요하지 않습니다. 기록하는 쪽은 알고 있지만
텍스트에는 없는 사실이기 때문입니다.

## 설치

```bash
pip install "Brain4Agent[precise]"   # recommended: adds jieba, hit@1 0.925
pip install Brain4Agent              # zero dependencies: bigrams only, hit@1 0.825
```

Windows와 macOS 모두 동작하며 Python 3.11 이상이 필요합니다. 패키지는
PyPI(<https://pypi.org/project/Brain4Agent/>)에 올라와 있습니다. 코드 자체를
수정하려면 `git clone` 후 `pip install -e ".[precise,dev]"`를 실행합니다.

`jieba`는 약 20 MB 크기의 정적 사전입니다. 필수는 아닙니다. 없으면 코드가 검색의
쓰기와 읽기 양쪽에서 바이그램으로 떨어지면서도 계속 동작합니다.

**Windows에서의 비ASCII 입력.** MCP 서버와 CLI는 stdin/stdout을 UTF-8로
고정하므로 콘솔 코드 페이지와 무관하게 CJK 내용이 동작합니다. 다만 명령줄
*인자*는 그 전에 Python이 디코딩합니다. 비ASCII 텍스트를 인자로 넘긴다면
`PYTHONUTF8=1`을 설정해야 합니다.

## 빠른 시작

### CLI

```bash
$ brain4agent exchange \
    "中文查询搜不到记忆，recall 返回空" \
    "根因在 keywords.py 第 443 行，正则不含汉字范围"
stored exchange in session 913bcac81341

$ brain4agent exchange \
    "杭州那台测试机的地址是 203.0.113.42" \
    "部署目录 /opt/demo-app，跑的是 PostgreSQL 14"
stored exchange in session c060a5294037

$ brain4agent search "中文查询为什么搜不到" -k 1
1 sessions for '中文查询为什么搜不到'
  [ 6.73 cov=1.00] 913bcac81341

--- 913bcac81341  score=6.73  coverage=1.00 ---
user: 中文查询搜不到记忆，recall 返回空
assistant: 根因在 keywords.py 第 443 行，正则不含汉字范围
```

저장소가 답할 수 없는 질문입니다.

```bash
$ brain4agent search "杭州测试机上装的是什么数据库" -k 1
1 sessions for '杭州测试机上装的是什么数据库'
  corpus has no: 数据库, 机上
  [ 4.81 cov=0.28] c060a5294037  session lacks: 数据库, 机上
```

기존 이력을 JSONL에서 대량으로 적재합니다(한 줄에 객체 하나, `content` 필수).

```bash
$ brain4agent import conversations.jsonl
imported 4 turns across 2 sessions
```

```jsonl
{"session_id": "s1", "role": "user", "content": "中文查询搜不到记忆"}
{"session_id": "s1", "role": "assistant", "content": "根因在 keywords.py 第 443 行"}
```

### MCP 서버

```json
{"mcpServers": {"brain4agent": {
    "command": "python",
    "args": ["-m", "brain4agent.mcp_server"],
    "env": {"BRAIN4AGENT_DB": "/path/to/brain.db"}
}}}
```

도구는 다섯 개입니다.

| 도구 | 용도 |
|---|---|
| `b4a_remember` | 턴 하나를 저장하고 세션 id를 반환합니다 |
| `b4a_recall` | 검색합니다. `corpus_missing`과 세션별 `missing_terms`를 함께 반환합니다 |
| `b4a_ask` | 검색과 답변을 한 번에 합니다. 모델이 필요하며, 없으면 그렇다고 말합니다 |
| `b4a_session` | 세션 전체를 순서대로 읽습니다 |
| `b4a_stats` | 집계 수치 |

`b4a_` 접두사는 의도한 것입니다. `remember`나 `recall` 같은 이름은 같은
클라이언트에 로드된 다른 MCP 서버와 충돌합니다.

이 서버는 stdio 위에서 MCP를 표준 라이브러리만으로 구현한 것입니다. 줄바꿈으로
구분된 JSON-RPC 메서드 네 개입니다. 공식 SDK는 사전 네 개를 직렬화하려고 거대한
의존성 트리를 끌어옵니다.
[D-017](docs/decisions.md#d-017-mcp-implemented-against-the-protocol-not-the-sdk)을
참고합니다.

같은 라이브러리는 에이전트 [skill](integrations/)로도 패키징되어 있습니다.
에이전트가 문서를 읽은 뒤 CLI를 호출하는 방식입니다.

### 라이브러리

```python
from brain4agent import MemoryStore

with MemoryStore("brain.db") as store:
    sid = store.new_session()
    store.add("杭州那台测试机的地址是 203.0.113.42", session_id=sid, role="user")
    store.add("部署目录 /opt/demo-app", session_id=sid, role="assistant")

    result = store.search("杭州测试机上装的是什么数据库")
    print(result.corpus_missing)        # ['数据库', '机上']
    print(result.best().coverage)       # 0.28
```

`add_exchange(user=..., assistant=...)`는 한 쌍을 하나의 세션으로 저장합니다.
검색은 턴 단위가 아니라 세션 단위입니다. 답은 대개 한 번의 주고받기를 가로지르고,
턴 하나만 심사하면 거짓 음성이 훨씬 많이 나옵니다.

대량 적재는 `batch()`를 거칩니다. 이 컨텍스트는 커밋을 그룹당 한 번으로
미룹니다.

```python
with store.batch():
    for turn in turns:
        store.add(turn.text, session_id=turn.sid, role=turn.role)
```

### 선택적 호스팅 심사자

기본값은 꺼짐입니다. 키가 있을 때만 켜집니다.

```python
from brain4agent import Judge, MemoryStore

judge = Judge.from_env()          # reads BRAIN4AGENT_JUDGE_KEY; None if unset
if judge:
    r = store.search_judged("question", judge)
    print(r.verdict)              # found / not_found / uncertain
```

`uncertain`은 별개의 세 번째 상태입니다. 심사자가 타임아웃되거나 503을 반환한
것은 기억이 없다는 증거가 아닙니다. 둘을 뭉개면 장애가 "이런 건 기록한 적
없습니다"라는 확신으로 바뀝니다.

## 동작 방식

```
                write                          read
                  │                              │
        bigrams + dictionary words          dictionary words
                  │                              │
                  ▼                              ▼
          ┌──────────────────────────────────────────┐
          │  SQLite: id, session, role, content,     │
          │          created_at, tokens              │
          └──────────────────────────────────────────┘
                  │                              │
                  ▼                              ▼
           BM25 index (in memory)  →  session-level evidence
                                        + corpus_missing
                                        + per-session coverage
```

### 저장

SQLite 파일 하나입니다. 행은 턴이고, 검색 단위는 세션입니다. 인덱스 토큰은 쓸 때
계산해 컬럼에 캐시하므로, 메모리 인덱스를 다시 만드는 일은 재분절이 아니라 개수
세기에 가깝습니다.

각 행에는 `tags`, `superseded_by`, `refs`, 그리고 선택적인 별도 인덱스 텍스트도
붙습니다. 호출자가 쓸 때 제공하고 저장소가 읽을 때 필터링하거나 확장하는
메타데이터입니다. PrecisionMemBench를 풀 수 있게 만드는 것이 바로 이것들이며,
없으면 같은 BM25가 0.3766을 기록합니다.

쓰기는 배치로 커밋합니다. 1,016턴 적재는 커밋을 하나씩 할 때 3.8초, `batch()`
안에서 0.25초가 걸렸습니다. 커밋 천 번의 비용이 쓰기 천 번보다 큽니다.

```
                       import    rebuild   query
127 turns   44 sessions          3.9 ms   1.8 ms
1016 turns  352 sessions  0.25 s  29 ms   3.7 ms
```

### 읽기/쓰기 토크나이저 분리

인덱싱과 질의는 다른 작업입니다. 쓰기는 모든 단서를 남기고 싶어 합니다. 모르는
단어에도 매칭 경로를 만들어 주는 바이그램까지 포함합니다. 질의는 잡음을 버리고
싶어 합니다. `杭州测试机`에서 `州测` 같은 것이 나오지 않아야 합니다.

인덱스 전략과 질의 전략의 3×3 조합으로 측정했습니다.

| 인덱스 | 질의 | hit@1 | MRR |
|---|---|---|---|
| bigram | bigram | 0.825 | 0.891 |
| jieba | jieba | 0.875 | 0.911 |
| **bigrams + words** | **words** | **0.925** | **0.940** |

비대칭 조합은 모두 대칭 조합을 이깁니다.
[D-019](docs/decisions.md#d-019-index-wide-query-narrow)를 참고합니다.

### 판정이 아니라 증거

저렴한 기권 신호는 모두 측정했지만 어느 것도 충분하지 않았습니다. 답할 수 있는
질의의 95%를 유지하는 지점에서 기권률은 BM25 점수나 IDF coverage 기준 약 10%,
열세 개 피처를 사용한 로지스틱 회귀 기준 21%에서 멈춥니다.

쓸 만한 신호 하나는 성격이 다릅니다. 점수가 아니라 사실입니다.

- **`corpus_missing`** — 질문의 내용어가 저장된 코퍼스 어디에도 나타나지
  않습니다. 이 세션에만 없는 것이 아니라 모든 세션에 없습니다.
- **`missing_terms`** (세션별) — *이* 세션이 왜 그 순위에 왔는지 보여줍니다.

이 구분이 중요합니다. `用户`와 `记忆`는 대부분의 개별 세션에는 없지만 코퍼스에는
있습니다. 그건 "이게 아니다"이지 "모른다"가 아닙니다. 둘을 혼동하면 답할 수 있는
질문 40개 중 27개를 잘못 거절했습니다.
[D-018](docs/decisions.md#d-018-corpus-absence-is-not-session-absence)을 참고합니다.

## 벤치마크

모든 수치는 `bench/` 스크립트로 재현할 수 있습니다. 이 스크립트들은 복사본이
아니라 실제 배포 코드를 임포트합니다.

### LongMemEval(영어) — 검색

`s` 변형에 대한 답 가능 질문 470개(평균 haystack 493턴), 문자 바이그램 기반
BM25:

```
hit@1    0.8660
hit@5    0.9511
hit@10   0.9660
MRR      0.8990
```

`python -m bench.run_longmemeval --dataset s`로 재현합니다. `bench/data/`는
커밋되지 않고 `bench/fetch_data.py`가 내려받습니다. 264 MB의 JSON은 git에 둘 것이
아니며, 페처는 이를 바이트 단위로 동일하게 재현합니다.

**이 벤치마크에서 검색은 어려운 부분이 아닙니다.** 답의 96.6%가 상위 열 개 안에
있습니다.

이
벤치마크에서는 성립하지만 다른 곳으로 옮겨지지 않습니다.

| 벤치마크 | 지표 | 이 저장소 | 최고 서드파티 |
|---|---|---|---|
| LongMemEval `s` | hit@10 | 0.9660 | — |
| PrecisionMemBench | active | **34/43** | 18/43 (open-knowledge-format) |
| PrecisionMemBench | total | **64/77** | 36/77 (open-knowledge-format) |
| LoCoMo | hit@1 | **0.6270** | 비교 불가(아래 참조) |

검색기는 셋 모두에서 같습니다. 다른 것은 질문이 무엇을 요구하는가입니다.
LongMemEval은 큰 haystack 위에서 넓은 질문을 하고 상위 열 개 안의 적중을
인정합니다. PrecisionMemBench는 정확히 옳은 신념만 돌아오는지를 묻고, 문서가
하나 더 붙으면 실패입니다. 전자에서는 검색이 풀린 문제이고, 후자에서는 공개된
최고 시스템도 절반을 넘기지 못합니다.

"검색은 쉽다"와 "검색은 어렵다"는 둘 다 참입니다. 어느 쪽을 얻는지는 무엇을
적중으로 세는지에 전적으로 달려 있습니다.

### PrecisionMemBench — 검색 정밀도

35개 신념에 대한 단일 턴 케이스 77개. 생성 모델도 심사자도 없습니다. 정답은
저장소가 반환한 신념 ID 집합 자체이고, 각 케이스는 어떤 ID가 들어가도 되고
들어가면 안 되는지를 단언합니다.

```
active  34/43 = 0.7907     cases that need query-dependent retrieval
 total  64/77 = 0.8312     including cases any store passes
```

숫자가 둘인 이유는 벤치마크가 둘을 보고하고, 둘이 서로 대체 가능하지 않기
때문입니다. **정직한 쪽은 `active`입니다.** 77개 케이스 중 33개는 빈 저장소로도
통과합니다. 그 단언들이 하네스가 코퍼스 자체에서 도출하는 계층(persona prelude,
고정 사실, 열린 질문)만 건드리기 때문입니다. `total`만 인용하면 이 저장소가 하지
않은 일까지 공으로 돌리게 됩니다.

벤치마크 자체 사이트(`tenureai.dev/benchmark`)의 공식 표입니다.

```
System                  Active    Total
----------------------  ------    -----
tenure (the authors)    43/43     77/77
this store              34/43     64/77
open-knowledge-format   18/43     36/77
atomicmemory             5/43     16/77
supermemory              2/43     15/77
yourmemory               0/43     21/77
gbrain                   0/43     11/77
hindsight                0/43     11/77
zep                      0/43      9/77
agentmemory              0/43      9/77
cognee                   0/43      9/77
mem0                     0/43      9/77
a-mem                    0/43      7/77
```

이 저장소는 두 열 모두에서 모든 서드파티 시스템을 앞섭니다. **벤치마크 자체의
참조 구현은 앞서지 못합니다.** 그 구현은 43/43과 77/77을 기록하며, 앞설 이유도
없습니다.

두 열은 분모가 다릅니다. 34/43 active는 34/77이 아닙니다. 그래서 둘 다 제시합니다.

이제 두 열을 나란히 제시하므로 비교가 다시 섞일 수 없습니다. 이것이 뒷받침하는
주장은 그것이 대체한 주장보다 좁습니다. "state of the art를 이겼다"가 아니라
**이 벤치마크에서 최고의 서드파티 결과**입니다.

### LoCoMo — 검색

272개 세션, 5882턴, 독립 대화 샘플 열 개에 대한 질문 1540개.

```
hit@1   0.6270
hit@5   0.8850
hit@10  0.9471
MRR     0.7369
```

`python -m bench.locomo.run` — 모델 없음, 데이터는 커밋되어 있습니다.

**공개된 LoCoMo 수치와 비교할 수 없습니다.** 그 수치(0.67–0.92)는 자체 백본과
프롬프트를 가진 LLM 심사자 아래의 답 정확도를 측정하고, 여기 수치는 올바른
세션이 검색되었는지를 측정합니다.

`hit@5 = 0.8850`은 누군가의 답 정확도 상한이 **아닙니다.** 정확히
다섯 개 세션만 보고 그 밖으로 추론하지 못하는 리더의 상한일 뿐입니다. 이 저장소
자체의 `hit@10 = 0.9471`이 이미 MemMachine의 0.9169를 넘습니다. 같은 저장소이므로
그 한계는 다른 시스템의 검색에 대해 아무 말도 하지 않습니다. 공개된 LoCoMo
수치는 어느 방향으로도 검색 품질의 증거가 아닙니다.

여기서의 설계 교훈은 검색 단위가 답의 단위와 맞아야 한다는 것입니다. 세션 대신
턴을 인덱싱하면 다른 변경 없이 hit@1이 8.2포인트 떨어집니다(0.5447 → 0.6270).

### 중국어 벤치마크

질문 59개(답 가능 40, 답 불가 19), 공유 코퍼스의 세션 44개, 처음부터 직접
구축했습니다. 조사한 논문 여덟 편 중 CJK 분절을 평가한 것은 없습니다.

| 지표 | bigram/bigram | bigrams+words / words |
|---|---|---|
| hit@1 | 0.825 | **0.925** |
| hit@5 | 0.950 | **0.975** |
| hit@10 | 1.000 | 1.000 |
| MRR | 0.891 | **0.940** |

hit@10은 포화 상태이고, hit@1과 MRR만 변별력을 가집니다.

### 그 수치가 버티지 못하는 지점

**0.925는 44개 세션을 설명합니다. 밀집한 근사 중복에서는 버티지 못합니다.**
같은 주제를 공유하지만 다른 사실을 말하는 잡음 세션 300개를 더하면 hit@1이 0으로
떨어집니다.

| 코퍼스 | hit@1 | hit@5 |
|---|---|---|
| 세션 44개 | 0.925 | 0.975 |
| 동일 주제 세션 +300개 | 0.000 | 0.000 |

메커니즘은 문자 그대로의 매칭입니다. *"근본 원인이 어느 파일 몇 행에 있는가"*를
물었다고 합시다. `keywords.py line 443`이라고 말한 세션에는 根因은 있어도 文件도
行도 없습니다. 반면 `looked at some file, some line`이라고 말한 세션에는 셋이 모두
있습니다. 모호한 비답변이 정확한 답변보다 위로 올라옵니다.

빠진 리터럴을 채워 넣어도 해결되지 않으며, 그것도 측정했습니다. 오라클 질의, 즉
질문에 골드 세션의 파일명·행 번호·커밋 해시를 더한 질의는 전체의 15%를
회복합니다.

| 질의 | hit@1 |
|---|---|
| 질문만 | 0.000 |
| 오라클 엔티티 3개 추가 | 0.150 |

낮게 유지되는 이유는 둘입니다. **40개 답변 중 23개에는 구체적인 토큰이 아예
없습니다**("다운스트림 컴포넌트에 변경이 필요했나?" — 답은 "아니오"). 채워 넣을
것이 없습니다. 나머지 17개에서도 BM25가 올바른 세션을 첫 자리에 올리는 비율은 절반에
못 미칩니다.

네 가지 수정을 측정하고 기각했습니다. BM25 길이 정규화(효과 없음), 최신성
타이브레이크(깨끗한 코퍼스에서 0.25 손실), 구체성 보너스(질문 하나 회복, 0.025
손실), 오라클 엔티티 주입입니다.
[D-020](docs/decisions.md#d-020-bag-of-words-retrieval-degrades-on-dense-same-topic-corpora)과
[D-021](docs/decisions.md#d-021-oracle-entities-recover-15-the-failure-is-not-missing-literals)을
참고합니다.

실무적 결론: BM25는 한 주제가 코퍼스에
한두 번 나올 때는 충분합니다. 그렇지 않을 때의 해법은 질의 시점이 아니라 쓰기
시점에 있습니다.

PrecisionMemBench가 반례입니다. 신념 35개, 거의 동일한
주제, 서로 다른 두 기억에 같은 단어 `redis`. 기억이 범위 태그, 대체 링크, 관계
refs를 갖추고 인덱스가 산문 대신 신념의 이름을 담으면, 같은 BM25가 거기서
0.8312를 기록합니다. 질의 측 수정 네 가지를 측정했지만 모두 실패했습니다. BM25
파라미터 스윕, coverage 임계값, 점수 비율, 누락 용어 비율입니다.

위의 0.000은 실제 값입니다. 모든 문서가 같은 주제를 다루는 코퍼스에서 *태그
없는* BM25가 보이는 결과입니다. 상위 다섯 개를 읽고, 원점수보다 `corpus_missing`에
무게를 두고, 기억에 라벨을 붙여야 합니다. 범위, kind, 무엇이 무엇을 대체하는지
입니다. 시스템이 판정 대신 증거를 돌려주는 이유가 여기에 있으며, 서로 독립적인
측정 세 번에서 나온 결론입니다.

### 기권

`corpus_missing`의 자연스러운 동작점에서:

| 전략 | 유지 | 기권 |
|---|---|---|
| 전부 답변 | 1.000 | 0.000 |
| **corpus_missing** | **0.875** | **0.632** |
| 로컬 9B 모델 | 0.950 | 0.895 |
| 호스팅 `deepseek-flash` | 0.925 | 1.000 |

0.875의 유지율은 답할 수 있는 질문의 12.5%를 자동으로 거절한다는 뜻입니다.
호출자를 대신해 결정하기에 충분하지 않습니다. 그래서 이 신호는 행동으로 옮기지
않고 보고만 합니다.

### 호스팅 심사자

내장 기권이 꼭 필요하다면, 메모리를 차지하지 않는 유일한 선택지는 호스팅
모델입니다.

| 접근 | 유지 | 기권 | 지연 시간 | 상주 메모리 |
|---|---|---|---|---|
| BM25만 | 1.000 | 0.000 | 0.22 ms | 0 |
| 로컬 2B | 0.750 | 1.000 | 0.77 s | ~1 GB |
| 로컬 9B | 0.950 | 0.895 | 1.5–2 s | 15.2 GB |
| `deepseek-flash` | 0.925 | 1.000 | 0.81 s | 0 |

작업 하나에서 메모리 조회 30회에 0.81초씩이면 24초의 추가 지연입니다. 호출
에이전트가 이미 추론하는 중에 스스로 내릴 수 있는 판단에 쓰이는 시간입니다.

### 이 중 얼마나가 표본 잡음인가

77개 케이스는 작은 벤치마크이고, 작은 벤치마크는 넓은 구간을 낳습니다. 그래서 이
페이지의 모든 수치에 Wilson 95% 구간을 붙였습니다.

| 결과 | 비율 | 95% CI | 폭 |
|---|---|---|---|
| PrecisionMemBench **active**, 이 저장소 | 34/43 = 0.7907 | 0.6479 – 0.8858 | 23.8 pp |
| PrecisionMemBench **active**, open-knowledge-format | 18/43 = 0.4186 | 0.2838 – 0.5667 | 28.3 pp |
| PrecisionMemBench **total**, 이 저장소 | 64/77 = 0.8312 | 0.7323 – 0.8986 | 16.6 pp |
| PrecisionMemBench **total**, open-knowledge-format | 36/77 = 0.4675 | 0.3603 – 0.5779 | 21.8 pp |
| 중국어 hit@1 (답 가능 40) | 37/40 = 0.9250 | 0.8014 – 0.9742 | 17.3 pp |
| LoCoMo hit@1 | 960/1531 = 0.6270 | 0.6025 – 0.6509 | 4.8 pp |
| LoCoMo hit@5 | 1355/1531 = 0.8850 | 0.8681 – 0.9001 | 3.2 pp |

구간이 넓은 것은 77개 케이스의 정직한 비용입니다. 비교는 **두** 분모 모두에서
유지되며, 둘은 서로 대체할 수 없기 때문에 이 점이 중요합니다.

- active: 하한 0.6479 대 상한 0.5667, 8포인트 격차
- total: 하한 0.7323 대 상한 0.5779, 15포인트 격차

어느 쌍도 겹치지 않습니다. 조심해서 다뤄야 할 것은 중국어 수치입니다. 40개 중
37개는 [0.80, 0.97]을 줍니다. 점추정값 0.925를 정밀한 값처럼 인용해서는 안
됩니다. 방향이지 값이 아닙니다.

이 표가 해결할 수 없는 두 가지가 있습니다. **PrecisionMemBench는 벤치마크
하나**입니다. 같은 형태의 두 번째 코퍼스가 효과를 확인해 주거나, 이 35개 신념에
국한된 현상임을 보여 줄 것입니다. 그리고 **0.8312를 독립적으로 재현한 곳은
없습니다.** 데이터와 하네스가 커밋되어 있으니 재현 가능하지만, 내가 재현할 수
있다는 것과 남이 재현했다는 것은 다릅니다.

## 다른 메모리 서버와 함께 실행하기

**같은 에이전트에 메모리 MCP 서버 두 개를 동시에 켜면 안 됩니다.** 측정
결과(D-031): `neural-memory`와 `b4a`를 모두 켠 상태에서 코드 스타일 관례를 물은
에이전트가 다른 서버를 조회하고 아무것도 얻지 못한 뒤 "메모리에 이 기록이
없다"고 보고했습니다. 그동안 관련 기억 다섯 개가 `b4a`에 있었습니다. 저장소는
내부에서 이 상황을 감지할 수 없습니다. 빈 메모리와 정확히 똑같이 보입니다.

직접 MCP 핸드셰이크로 `b4a`가 정상임을 확인했으므로, 실패는 검색이 아니라 선택
단계에 있었습니다. 에이전트당 메모리 서버 하나, 또는 선택이 모호하지 않게 만드는
이름이 답입니다. MCP 도구를 서버별로 네임스페이스하는
하네스(mcp__b4a__b4a_recall)는 이 문제를 겪지 않습니다. 충돌은 비슷한 이름의
메모리 도구를 노출하는 서버가 둘일 때 생깁니다.

## 최전선과 비교

현재 에이전트 메모리 지형에서 이 프로젝트가 어디에 있는지 분명히 적습니다. 장점만
나열하는 README는 판촉 페이지이기 때문입니다.

| 기능 | 이 저장소의 상태 |
|---|---|
| 구조화된 기억 (타입이 있는 사실, 선호, 엔티티) | **부분적.** `kind`는 자유 형식 라벨, `tags`는 범위, `refs`는 링크입니다. 스키마도 검증도 없습니다. kind의 의미는 호출자가 정합니다. |
| 시간·그래프 기억 (유효 구간, 관계 진화) | **미구현.** `created_at`이 있고 `superseded_by`가 대체를 기록하지만, 유효 구간도 질의 시점 그래프 순회도 없습니다. 그래프를 만들어 중국어 코퍼스에서 측정했고 아무것도 바뀌지 않았습니다(D-024). 그래서 연결하지 않았습니다. `refs`는 한 홉 확장이지 순회가 아닙니다. |
| 충돌 해결 | **구현됨, 결정적.** `supersede(old, new)`를 사용하며, 대체된 기억은 더 이상 나타나지 않습니다. 모델이 개입하지 않습니다. PrecisionMemBench 대체 카테고리: 3/3. |
| 쓰기 경로 중복 제거 / 패턴 추출 | **미구현.** 추출 기능은 있고(`remember()`), **기본값은 꺼져 있습니다.** 쓰기 시점에 측정했을 때 검색 성능을 깎기 때문입니다(D-023). |
| 다중 검색기 융합 | **미구현.** 검색기는 하나입니다. 바이그램과 선택적 jieba 단어 위의 BM25. |
| 망각 / 통합 | **조악함.** `prune(keep_sessions=N)`은 검색 개선이 아니라 최신성 기반 크기 제어입니다. 잡음 많은 코퍼스를 되살리려면 95%를 삭제해야 합니다. 비우는 것이지 망각이 아닙니다(D-022). |
| 세션 간 집계 | **미구현.** 지금까지는 명시적으로 범위 밖입니다. |
| 능동적 리콜 | **부분적.** `recall-context`는 stdin에서 프롬프트를 읽어 형식화된 기억을 출력하고, 맞는 것이 없으면 조용합니다. 클라이언트 측 훅을 위해 만들었습니다. MCP는 풀 방식뿐이라 서버가 먼저 기억을 내밀 수 없습니다. 스케줄러는 없습니다. 언제 실행할지는 클라이언트가 정합니다. `integrations/hooks/`를 참고합니다. |
| 멀티모달 | **미구현.** |
| 환각 방어 | **부분적.** 증거/판정 분리, `corpus_missing`, 세 가지 상태로 나뉜 심사 결과. 올바른 검색에서 나온 틀린 답을 탐지하는 것은 없습니다. |
| 공개 수치의 재현성 | **강함.** 벤치마크 셋, 그중 둘은 루프에 모델이 전혀 없습니다. 이 프로젝트가 분야 대부분보다 앞서는 축이며, 목표 자체가 아니라 모델 없음 원칙의 결과입니다. |

정직한 요약: **이것은 측정을 유난히 꼼꼼히 한 검색 계층이지 인지 아키텍처가
아닙니다.** 하는 일은 하나입니다. 올바른 기억을 찾아 무엇을 찾았고 무엇을 찾지
못했는지 분명히 말하는 것. 나머지는 의도적으로 거절합니다. 그 교환이 옳은지는
호출자에 달려 있습니다. 이미 모델을 가진 에이전트는 증거와 깔끔한 기권 신호를
원하지, 자기 기억에 대한 두 번째 모델의 의견을 원하지 않습니다.

## 현황

라이브러리, CLI, MCP 서버는 완성되어 있습니다. 메타데이터 계층(범위 태그, 대체
링크, 관계 refs, 별도 인덱스 텍스트)은 첫 벤치마크를 쓴 뒤에 들어왔습니다.

**의도적으로 만들지 않았고, 계획도 없습니다:**

- **세션 간 자동 병합.** 검색은 이미 세션을 가로지릅니다. 질의 하나가 저장된 모든
  세션을 검색하고 그중 최선을 반환합니다. 만들어지지 않은 것은 여러 세션을 하나의
  요약으로 *합성*하는 일입니다. 모델이 필요하거나, 두 기억이 같은 것을 설명한다고
  판정하는 규칙이 필요합니다. 잘못 병합하면 리더가 직접 저울질할 수 있었던 세부가
  사라집니다.
- **멀티모달.** 범위 밖입니다.

**최근 추가:**

- **근사 중복 탐지.** 기억마다 SimHash 지문을 붙이고, 두 기억이 같은 것을 말할 수
  있으면 `duplicates_of(id)`가 반환합니다(검색 경로에서는 돌지 않습니다. 전체 스캔은
  2,893건에서 5 ms로 쿼리 시간의 절반이 넘습니다). 보고만 하고 병합하지
  않습니다. 호출 에이전트가 둘 다 읽고 판단합니다(D-028).
- **가중치.** `reinforce`가 올리고, `decay`가 내리고, `prune_by_weight`가 임계값
  아래로 떨어진 것을 삭제합니다. 나이와 무관한 첫 망각 신호입니다. 검색된 기억은
  살아남고, 검색되지 않은 기억은 감쇠합니다(D-029).

**최근 수정:**

- **대체된 기억이 사라지곤 했습니다.** `supersede(old, new)`는 옛 기억을
  숨겼는데, 새 기억이 다른 단어를 쓸 때("주 저장소는 MySQL"이 "PostgreSQL로
  이전"으로 대체됨) "주 저장소" 질의는 숨겨진 쪽에만 매칭되어 검색이 아무것도
  반환하지 않았습니다. 갱신되는 순간 사실을 잊는 기억 시스템은 그 사실을 처음부터
  갖지 않았던 시스템보다 나쁩니다. 이제 적중은 버려지지 않고 현재 기억으로
  리다이렉트됩니다(D-027).

**미구현, 목록에 있음:**

- **시간 감쇠 망각.** `prune`은 최신성 기반 크기 제어입니다. D-022는 잡음 많은
  코퍼스를 되살리려면 95%를 삭제해야 함을 측정했습니다. 나이 대신 중요도를
  저울질하는 감쇠가 다음 실제 작업입니다.
- **리콜 스케줄러.** 훅을 위한 `recall-context`는 있지만 언제 실행할지 정하는
  것이 없습니다. 매 턴 실행은 저렴하지만(1.5 ms) 아마 너무 시끄러울 것입니다.
- **빈도 기반 랭킹.** `accesses`는 집계되고 `weight`는 `weight_blend`를 통해
  랭킹에 섞일 수 있지만 기본값은 꺼져 있습니다. 메커니즘은 테스트했지만 *도움이
  되는지*는 측정하지 않았습니다. 측정하지 않은 신호로 결과 순서를 바꾸는 것은 이
  프로젝트가 계속 거부해 온 종류의 변경입니다.
- **다중 검색기 융합.** 지금은 BM25 하나입니다. 모델 없음 원칙을 깨지 않고 두 번째
  어휘 검색기를 시도할 수는 있습니다.
- **`kind`의 스키마.** 검증 없는 자유 형식 문자열입니다.

**측정 후 기각 — 보류가 아니라 결정:**

- **질의 시점 그래프 순회.** 만들어 중국어 코퍼스에서 측정했고 아무것도 바뀌지
  않았습니다(D-024). 한 홉 `refs` 확장은 도움이 됩니다. PrecisionMemBench에서
  4/4입니다. 하지만 그것은 링크이지 순회가 아닙니다.
- **쓰기 시점 추출.** 검색 성능을 깎기 때문에 기본값이 꺼져 있습니다(D-023).

**모델 없이는 닿을 수 없음:**

- **올바른 검색에서 나온 틀린 답의 탐지.** 여기의 모든 신호는 올바른 기억이
  돌아왔는지를 말합니다. 리더가 그것을 잘 썼는지는 아무도 말하지 않습니다.
  심사자가 필요하고, 틀린 심사자는 없는 것보다 나쁩니다.

[결정 로그](docs/decisions.md)는 양방향으로 34개 항목을 기록합니다. 테스트했다가
실패한 가설도 포함됩니다. [연구 노트](docs/research.md)와
[지형 분석](docs/landscape.md)은 주변 분야를 다룹니다.

알려진 한계는 모두 측정된 것입니다. 태그 없는 검색은 밀집한 근사 중복에서 성능이
떨어지고(D-020), 어떤 질의 측 기법으로도 회복되지 않습니다(D-021). 해법은 쓰기
시점에 있습니다(D-025, D-026). LoCoMo hit@1은 0.6270으로, 그 데이터셋에서 공개된
최고 답 정확도를 넘지 못합니다. 그리고 그 격차는 읽기가 아니라 검색에서 옵니다.

[`docs/decisions.md`](docs/decisions.md)에 있습니다. 양방향이 모두 기록됩니다.
테스트했다가 실패한 가설도 포함됩니다.

## 기여

검증 게이트:

```bash
python -m pytest tests/ -q
python -m ruff check src bench tests
python -m ruff format --check src bench tests
python -m bench.zh.e2e
python -m bench.pmb.run
python -m bench.locomo.run
```

`bench/zh/e2e.py`는 실제 배포 코드 경로를 실행하며 `hit@1 0.9250`을 보고해야
합니다. `bench.pmb.run`은 `pass 64/77`, `bench.locomo.run`은 `hit@1 0.6270`을
보고해야 합니다. 검색, 토큰화, 스코어링 변경이 이 중 하나라도 낮추면 회귀입니다.
마지막 둘은 API 키도 네트워크도 필요하지 않습니다.

설계 결정을 바꾸려면 `docs/decisions.md`에 새 항목으로 넣고, 그것을 정당화하는
측정을 함께 적어야 합니다.

## 특별 감사

[nhadaututtheky](https://github.com/nhadaututtheky)님과
[neural-memory](https://github.com/nhadaututtheky/neural-memory)에 감사를
전합니다. 이 프로젝트는 그곳의 버그 수정에서
시작했습니다([PR #228](https://github.com/nhadaututtheky/neural-memory/pull/228)).
중국어 질의가 아무것도 반환하지 않았고, 원인은 키워드 정규식에 한자 범위가 없었던
것입니다. 고쳐 보니 문제는 문자 클래스가 아니라 가정이었습니다. 그래서 이것은 같은
질문에 대한 다른 답이지 대체물이 아닙니다. neural-memory의 brain은 `bench/nmem/`의
코퍼스이기도 하며, 사용자가 실제로 무엇을 요청했는지 기록한 이곳의 유일한
데이터셋입니다.
