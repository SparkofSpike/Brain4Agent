# Brain4Agent

[English](README.md) | [简体中文](README.zh-CN.md) | **日本語** | [한국어](README.ko.md)

エージェントのための長期記憶。CJK を第一に扱う検索、コア経路にモデルを置かない設計、
そして信頼スコアの代わりに証拠を返すこと。

`pip install -e ".[precise]"` には Python 3.11 以降と、任意の辞書がひとつ要る。
辞書がなくても、すべては動作する。

## これは何か

コードベースで作業するエージェントは文脈を溜め込む。なぜその決定をしたのか、
どのやり方が失敗したのか、デプロイはどこにあるのか。その文脈は生まれた会話より
長生きし、導出し直すのは高くつく。

Brain4Agent はそうしたやり取りを単一の SQLite ファイルに保存し、セッション単位で
検索する。設計は四つの制約を軸にしている:

- **CJK はそのまま動く。** 漢字・かな・ハングルを空白や非単語境界で分割すると、
  クエリは一つのトークンに潰れる。半角カタカナは CJK の範囲にも ASCII の単語クラスにも
  一致しない。文字バイグラムにはどちらの問題も起きない。測定値は中国語のものだ
  （ベンチマーク参照）。日本語・韓国語・ベトナム語は対応しテストもしているが、
  ベンチマークは取っていない。README はその点を偽らない。
- **コアはモデルを呼ばない。** 検索は BM25。API キーもアクセラレータもコールドスタートも
  なく、クエリあたり一桁ミリ秒。
- **返すのは判定ではなく証拠だ。** 信頼スコアの代わりに、検索は質問中のどの語が
  コーパスに一度も現れなかったかを返す。その意味をどう取るかは呼び出し側に委ねられる。
  呼び出し側にはすでにモデルがある。
- **保存するものと索引するものは別だ。** 記憶は人間やリーダーが読むための全文を保ち、
  索引はより狭く、より識別性の高いものを持てる。両者を分けるだけで PrecisionMemBench は
  0.6104 から 0.7922 へ上がった。他の変更はない。説明的な文章はその領域全体と共有する
  平凡な語を持ち、唯一の識別名より上位に来てしまうからだ。

記憶はさらに `tags`（スコープ）、`superseded_by`（置換）、`refs`（一ホップのリンク）を持つ。
いずれも推論されたものではなく、モデルも要らない。書き手が知っていて、本文が語らない
事実だからだ。

## インストール

```bash
pip install "Brain4Agent[precise]"   # recommended: adds jieba, hit@1 0.925
pip install Brain4Agent              # zero dependencies: bigrams only, hit@1 0.825
```

Windows と macOS の両方で動く。Python 3.11 以降が必要だ。パッケージは PyPI に
<https://pypi.org/project/Brain4Agent/> としてある。コード自体を触るなら `git clone` して
`pip install -e ".[precise,dev]"`。

`jieba` は約 20 MB の静的辞書だ。必須ではない。なくてもコードは検索の書き込み側・
クエリ側の両方でバイグラムに落ちて、動作を続ける。

**Windows での非 ASCII 入力。** MCP サーバーと CLI は標準入出力を UTF-8 に固定するので、
コンソールのコードページに関係なく CJK を扱える。ただしコマンドラインの*引数*は、
その設定が効く前に Python がデコードする。非 ASCII 文字列を引数で渡す場合は
`PYTHONUTF8=1` を設定すること。

## クイックスタート

### CLI

```bash
$ brain4agent exchange \
    "中文查询搜不到记忆，recall 返回空" \
    "根因在 keywords.py 第 443 行，正则不含汉字范围"
stored exchange in session 913bcac81341

$ brain4agent exchange \
    "杭州那台测试机的地址是 203.0.113.42" \
    "部署目录 /opt/demo-app，跑的是 PostgreSQL 14"
stored exchange in session c060a5294037

$ brain4agent search "中文查询为什么搜不到" -k 1
1 sessions for '中文查询为什么搜不到'
  [ 6.73 cov=1.00] 913bcac81341

--- 913bcac81341  score=6.73  coverage=1.00 ---
user: 中文查询搜不到记忆，recall 返回空
assistant: 根因在 keywords.py 第 443 行，正则不含汉字范围
```

ストアが答えられない質問:

```bash
$ brain4agent search "杭州测试机上装的是什么数据库" -k 1
1 sessions for '杭州测试机上装的是什么数据库'
  corpus has no: 数据库, 机上
  [ 4.81 cov=0.28] c060a5294037  session lacks: 数据库, 机上
```

既存の履歴を JSONL から一括で読み込む（1 行 1 オブジェクト、`content` は必須）:

```bash
$ brain4agent import conversations.jsonl
imported 4 turns across 2 sessions
```

```jsonl
{"session_id": "s1", "role": "user", "content": "中文查询搜不到记忆"}
{"session_id": "s1", "role": "assistant", "content": "根因在 keywords.py 第 443 行"}
```

### MCP サーバー

```json
{"mcpServers": {"brain4agent": {
    "command": "python",
    "args": ["-m", "brain4agent.mcp_server"],
    "env": {"BRAIN4AGENT_DB": "/path/to/brain.db"}
}}}
```

ツールは五つ:

| ツール | 用途 |
|---|---|
| `b4a_remember` | 1 ターンを保存し、セッション ID を返す |
| `b4a_recall` | 検索し、`corpus_missing` とセッションごとの `missing_terms` を伴うセッションを返す |
| `b4a_ask` | 検索と回答を一度に行う。モデルが必要で、未設定ならその旨を返す |
| `b4a_session` | セッション全体を順に読む |
| `b4a_stats` | 件数 |

`b4a_` の接頭辞は意図的だ。`remember` や `recall` のような名前は、同じクライアントに
読み込まれた他の MCP サーバーと衝突する。

サーバーは stdio 上の MCP を標準ライブラリだけで実装したものだ。改行区切りの
JSON-RPC の 4 メソッドで動く。公式 SDK は四つの辞書をシリアライズするために
巨大な依存ツリーを引き込む。
[D-017](docs/decisions.md#d-017-mcp-implemented-against-the-protocol-not-the-sdk) を参照。

同じライブラリはエージェント向けの [skill](integrations/) としても配布している。
エージェントが読んでから CLI を呼ぶドキュメントだ。

### ライブラリ

```python
from brain4agent import MemoryStore

with MemoryStore("brain.db") as store:
    sid = store.new_session()
    store.add("杭州那台测试机的地址是 203.0.113.42", session_id=sid, role="user")
    store.add("部署目录 /opt/demo-app", session_id=sid, role="assistant")

    result = store.search("杭州测试机上装的是什么数据库")
    print(result.corpus_missing)        # ['数据库', '机上']
    print(result.best().coverage)       # 0.28
```

`add_exchange(user=..., assistant=...)` は一組をひとつのセッションとして保存する。
検索はターン単位ではなくセッション単位だ。答えは往復にまたがることが多く、
単一ターンで判定すると偽陰性がはるかに増える。

一括インポートは `batch()` を通す。コミットをグループごとに一度へ遅延させる:

```python
with store.batch():
    for turn in turns:
        store.add(turn.text, session_id=turn.sid, role=turn.role)
```

### 任意のホスト型ジャッジ

既定では無効。キーがあるときだけ有効になる。

```python
from brain4agent import Judge, MemoryStore

judge = Judge.from_env()          # reads BRAIN4AGENT_JUDGE_KEY; None if unset
if judge:
    r = store.search_judged("question", judge)
    print(r.verdict)              # found / not_found / uncertain
```

`uncertain` は独立した第三の状態だ。タイムアウトしたり 503 を返したりするジャッジは、
記憶が存在しない証拠にはならない。両者を潰すと、障害が「そんな記録はない」という
自信に変わってしまう。

## 仕組み

```
                write                          read
                  │                              │
        bigrams + dictionary words          dictionary words
                  │                              │
                  ▼                              ▼
          ┌──────────────────────────────────────────┐
          │  SQLite: id, session, role, content,     │
          │          created_at, tokens              │
          └──────────────────────────────────────────┘
                  │                              │
                  ▼                              ▼
           BM25 index (in memory)  →  session-level evidence
                                        + corpus_missing
                                        + per-session coverage
```

### ストレージ

SQLite ファイルはひとつ。行はターンで、検索の単位はセッションだ。索引トークンは
書き込み時に計算してカラムにキャッシュするので、インメモリ索引の再構築は
再分割ではなく数え直しで済む。

各行は `tags`、`superseded_by`、`refs` と、任意の別索引テキストも持つ。呼び出し側が
書き込み時に渡すメタデータで、ストアは読み取り時にそれをフィルタし展開する。
PrecisionMemBench がそもそも解けるのはこれらがあるからだ。なければ同じ BM25 で
0.3766 になる。

書き込みはバッチでコミットする。1,016 ターンのインポートは、1 回ずつコミットすると
3.8 秒、`batch()` の中なら 0.25 秒だった。千回の個別コミットは、千回の書き込みその
ものより高くつく。

```
                       import    rebuild   query
127 turns   44 sessions          3.9 ms   1.8 ms
1016 turns  352 sessions  0.25 s  29 ms   3.7 ms
```

### 読み書きで分割したトークナイザ

索引付けとクエリは別の仕事だ。書き込み側は手がかりをすべて残したい。未知語に
一致経路を与えるバイグラムも含めて。クエリ側はノイズを落としたい。`杭州测试机` から
`州测` を拾わないように。

索引戦略とクエリ戦略の 3×3 の組み合わせで測定した:

| 索引 | クエリ | hit@1 | MRR |
|---|---|---|---|
| bigram | bigram | 0.825 | 0.891 |
| jieba | jieba | 0.875 | 0.911 |
| **bigrams + words** | **words** | **0.925** | **0.940** |

非対称な組み合わせはすべて対称なものに勝つ。
[D-019](docs/decisions.md#d-019-index-wide-query-narrow) を参照。

### 判定ではなく証拠

安価な棄権シグナルはすべて測定したが、どれも十分ではなかった。答えられるクエリの
95% を維持した条件で、拒否率は BM25 スコアや IDF coverage で 10% 前後、13 特徴の
ロジスティック回帰で 21% が上限だった。

有用なシグナルは種類が違う。スコアではなく、事実だ:

- **`corpus_missing`** — 質問中の内容語が、保存済みコーパスのどこにも現れない。
  このセッションだけになく、すべてのセッションにない。
- **`missing_terms`**（セッションごと）— *この* セッションがその順位になった理由。

この区別は重要だ。`用户` と `记忆` は個々のセッションの多くにはないが、コーパスには
存在する。それは「これではない」という意味で、「分からない」ではない。両者を混同すると、
答えられる 40 問のうち 27 問を誤って拒否した。
[D-018](docs/decisions.md#d-018-corpus-absence-is-not-session-absence) を参照。

## ベンチマーク

すべての数値は `bench/` のスクリプトから再現できる。スクリプトは出荷コードのコピー
ではなく、出荷コードそのものをインポートする。

### LongMemEval（英語）— 検索

`s` バリアントに対する 470 の回答可能な質問（平均ハイスタック 493 ターン）、
文字バイグラム上の BM25:

```
hit@1    0.8660
hit@5    0.9511
hit@10   0.9660
MRR      0.8990
```

`python -m bench.run_longmemeval --dataset s` で再現できる。`bench/data/` はコミット
せず `bench/fetch_data.py` が取得する。264 MB の JSON は git に置くものではないし、
取得スクリプトはバイト単位で同じものを再現する。

**このベンチマークでは、検索は難しい部分ではない。** 答えの 96.6% が上位 10 件に入る。

成り立つのは
このベンチマークだけで、他へ移せるものではない:

| ベンチマーク | 指標 | このストア | 最高の第三者 |
|---|---|---|---|
| LongMemEval `s` | hit@10 | 0.9660 | — |
| PrecisionMemBench | active | **34/43** | 18/43 (open-knowledge-format) |
| PrecisionMemBench | total | **64/77** | 36/77 (open-knowledge-format) |
| LoCoMo | hit@1 | **0.6270** | 比較不能（下記） |

検索器は三つとも同じだ。違うのは、質問が何を求めているか。LongMemEval は大きな
ハイスタックに対する広い質問で、上位 10 件に入れば正解とする。PrecisionMemBench は、
まさに正しい belief だけが返るかを見る。余計な文書が一つあれば不合格だ。前者では
検索は解決済みで、後者では公開されている最良のシステムでも半分も当たらない。

「検索は簡単だ」と「検索は難しい」はどちらも正しい。どちらになるかは、何を正解と
数えるかで完全に決まる。

### PrecisionMemBench — 検索精度

35 の belief に対する 77 の単一ターンケース。生成モデルもジャッジもない。答えは
ストアが返す belief ID の集合そのもので、各ケースはどの ID が入ってよく、どれが
入ってはいけないかを表明する。

```
active  34/43 = 0.7907     cases that need query-dependent retrieval
 total  64/77 = 0.8312     including cases any store passes
```

数字が二つあるのは、ベンチマークが二つ報告し、両者が交換可能ではないからだ。
**正直なのは `active` のほうだ**。77 ケースのうち 33 は空のストアでも通る。その表明が、
ハーネスがコーパス自体から導出する層（ペルソナ前置き、固定事実、オープンクエスチョン）
にしか触れていないからだ。`total` だけを引くと、このストアがやっていない仕事を
手柄にすることになる。

公式の表。ベンチマーク自身のサイト（`tenureai.dev/benchmark`）より:

```
System                  Active    Total
----------------------  ------    -----
tenure (the authors)    43/43     77/77
this store              34/43     64/77
open-knowledge-format   18/43     36/77
atomicmemory             5/43     16/77
supermemory              2/43     15/77
yourmemory               0/43     21/77
gbrain                   0/43     11/77
hindsight                0/43     11/77
zep                      0/43      9/77
agentmemory              0/43      9/77
cognee                   0/43      9/77
mem0                     0/43      9/77
a-mem                    0/43      7/77
```

このストアは両方の列で第三者システムすべてに勝つ。**ベンチマーク自身の参照実装には
勝てない。** それは 43/43 と 77/77 で、勝てるはずの理由もない。

二つの列は分母が違う。34/43 active は 34/77 ではない。両方を並べて示す。
18/43 = 0.4186 だ。

いまは両方の列を並べて示すので、比較を混ぜることはできない。これが支える主張は、
置き換えたものより狭い。**このベンチマークにおける第三者最高成績**であって、
「最先端に勝った」ではない。

### LoCoMo — 検索

272 セッション、5882 ターン、10 個の独立した会話サンプルに対する 1540 の質問。

```
hit@1   0.6270
hit@5   0.8850
hit@10  0.9471
MRR     0.7369
```

`python -m bench.locomo.run` — モデルなし、データはコミット済み。

**公開されている LoCoMo の数値とは比較できない。** あちら（0.67–0.92）は、独自の
バックボーンとプロンプトを持つ LLM ジャッジ下での回答精度を測っている。こちらは
正しいセッションが検索されたかどうかを測る。

誘い込まれやすい推論について、注意しておく。この README はそれをやって間違えた。`hit@5 = 0.8850` は
誰かの回答精度の上限では**ない**。ちょうど 5 セッションだけを見て、その外で推論する
ことを禁じられたリーダーの上限でしかない。このストア自身の `hit@10 = 0.9471` はすでに
MemMachine の 0.9169 を上回っている。同じストアなのだから、この上限は別システムの
検索について何も語らない。公開 LoCoMo 数値は、どちらの方向にも検索品質の証拠に
ならない。

ここから得られる設計上の教訓は、検索の単位を答えの単位に合わせることだ。セッション
ではなくターンを索引すると、他を何も変えずに hit@1 が 8.2 ポイント落ちる
（0.5447 → 0.6270）。

### 中国語ベンチマーク

59 問（40 は回答可能、19 は回答不能）、共有コーパスの 44 セッション。ゼロから作った。
調査した 8 本の論文はいずれも CJK の分割を評価していない。

| 指標 | bigram/bigram | bigrams+words / words |
|---|---|---|
| hit@1 | 0.825 | **0.925** |
| hit@5 | 0.950 | **0.975** |
| hit@10 | 1.000 | 1.000 |
| MRR | 0.891 | **0.940** |

hit@10 は飽和している。判別力があるのは hit@1 と MRR だけだ。

### その数字が成り立たなくなる範囲

**0.925 が記述しているのは 44 セッションだ。密な近似重複には耐えない。** 話題は共有する
が別の事実を述べるノイズセッションを 300 加えると、hit@1 はゼロになる:

| コーパス | hit@1 | hit@5 |
|---|---|---|
| 44 セッション | 0.925 | 0.975 |
| +同一話題の 300 セッション | 0.000 | 0.000 |

仕組みは文字通りの一致だ。*「根本原因はどのファイルの何行目か」* と問うと、
`keywords.py line 443` と言うセッションは 根因 を含むが 文件 も 行 も含まない。
`looked at some file, some line` と言うセッションは三つとも含む。曖昧な非回答が、
正確な回答より上位に来る。

欠けているリテラルを補っても直らない。これも測定した。オラクルクエリ、つまり質問に
正解セッション自身のファイル名・行番号・コミットハッシュを足したものは、集合の
15% しか回復しない:

| クエリ | hit@1 |
|---|---|
| 質問のみ | 0.000 |
| + オラクル実体 3 つ | 0.150 |

低いままなのは二つの理由から。**40 の回答のうち 23 は具体的なトークンをまったく
含まない**（「下流のコンポーネントは変更が必要だったか」——答えは「いいえ」）。
補うものが何もない。残る 17 でも、BM25 が正しいセッションを 1 位にするのは
半分に満たない。

四つの修正を測って却下した。BM25 の長さ正規化（効果なし）、新近性のタイブレーク
（きれいなコーパスで 0.25 の損失）、具体性ボーナス（1 問を回復し、0.025 の損失）、
オラクル実体の注入。
[D-020](docs/decisions.md#d-020-bag-of-words-retrieval-degrades-on-dense-same-topic-corpora)
と [D-021](docs/decisions.md#d-021-oracle-entities-recover-15-the-failure-is-not-missing-literals) を参照。

実務上の帰結：話題がコーパスに一度か二度しか
現れないなら BM25 で足りる。そうでない場合、修正はクエリ時ではなく書き込み時にある。

反例が PrecisionMemBench だ。35 の belief、ほぼ同一の主語、同じ語 `redis` が
二つの異なる記憶に現れる。記憶がスコープタグ、置換リンク、関係 refs を持ち、索引が
belief の文章ではなく名前を保持すれば、同じ BM25 がそこで 0.8312 を出す。クエリ側の
修正は四つ測って、すべて失敗した。BM25 のパラメータ掃引、coverage しきい値、スコア比、
missing-term 比。

上の 0.000 は現実だ。すべての文書が同じ主題について語るコーパスに、*タグなしの* BM25 が
下す結果である。上位 5 件を読み、生スコアより `corpus_missing` を重く見て、記憶に
ラベルを付けること。スコープ、kind、何が何を置き換えるか。システムが判定ではなく
証拠を返すのは、独立した三つの測定からそうなっている。

### 棄権

`corpus_missing` の自然な動作点で:

| 戦略 | 維持 | 拒否 |
|---|---|---|
| すべてに答える | 1.000 | 0.000 |
| **corpus_missing** | **0.875** | **0.632** |
| ローカル 9B モデル | 0.950 | 0.895 |
| ホスト型 `deepseek-flash` | 0.925 | 1.000 |

維持率 0.875 は、答えられる質問の 12.5% が自動的に拒否されることを意味する。
呼び出し側の代わりに決めるには十分ではない。だからこのシグナルは作用させるのでは
なく報告する。

### ホスト型ジャッジ

組み込みの棄権が必要なら、メモリを消費しない唯一の選択肢はホスト型モデルだ:

| 手法 | 維持 | 拒否 | レイテンシ | 常駐 |
|---|---|---|---|---|
| BM25 のみ | 1.000 | 0.000 | 0.22 ms | 0 |
| ローカル 2B | 0.750 | 1.000 | 0.77 s | ~1 GB |
| ローカル 9B | 0.950 | 0.895 | 1.5–2 s | 15.2 GB |
| `deepseek-flash` | 0.925 | 1.000 | 0.81 s | 0 |

0.81 秒 × タスク内の 30 回のメモリ参照は 24 秒の追加レイテンシになる。しかもその
判定は、呼び出し側のエージェントがすでに推論しながら下せるものだ。

### このうちどれだけがサンプリングノイズか

77 ケースは小さなベンチマークで、小さなベンチマークは広い区間を生む。このページの
すべての数値に Wilson 95% 区間を付ける:

| 結果 | 比率 | 95% CI | 幅 |
|---|---|---|---|
| PrecisionMemBench **active**、このストア | 34/43 = 0.7907 | 0.6479 – 0.8858 | 23.8 pp |
| PrecisionMemBench **active**、open-knowledge-format | 18/43 = 0.4186 | 0.2838 – 0.5667 | 28.3 pp |
| PrecisionMemBench **total**、このストア | 64/77 = 0.8312 | 0.7323 – 0.8986 | 16.6 pp |
| PrecisionMemBench **total**、open-knowledge-format | 36/77 = 0.4675 | 0.3603 – 0.5779 | 21.8 pp |
| 中国語 hit@1（回答可能 40） | 37/40 = 0.9250 | 0.8014 – 0.9742 | 17.3 pp |
| LoCoMo hit@1 | 960/1531 = 0.6270 | 0.6025 – 0.6509 | 4.8 pp |
| LoCoMo hit@5 | 1355/1531 = 0.8850 | 0.8681 – 0.9001 | 3.2 pp |

区間は広い。それが 77 ケースという正直なコストだ。それでも比較は**両方**の分母で
成り立つ。両者が交換可能でない以上、これは重要だ:

- active: 下限 0.6479 対 上限 0.5667 で、8 ポイントの差
- total: 下限 0.7323 対 上限 0.5779 で、15 ポイントの差

どちらの組も重ならない。慎重に扱うべきは中国語の数値だ。40 中 37 は [0.80, 0.97] を
与える。点推定の 0.925 を、精密であるかのように引用してはいけない。それは方向で
あって値ではない。

この表が直せないことが二つある。**PrecisionMemBench は一つのベンチマークにすぎない。**
同じ形の第二のコーパスが、効果を確認するか、この 35 の belief に固有だったと示すかの
どちらかだろう。そして **0.8312 を独立に再現した者はいない。** データとハーネスは
コミットされているので再現可能だが、自分で再現できることは、他人が再現したこととは
違う。

## 別のメモリサーバーとの併用

**同じエージェントに二つのメモリ MCP サーバーを有効にしてはいけない。** 測定済み
（D-031）。`neural-memory` と `b4a` の両方を有効にした状態で、コードスタイルの慣習に
ついて尋ねられたエージェントは、もう一方のサーバーに問い合わせ、何も得られず、
「メモリに記録はない」と報告した。`b4a` には関連する記憶が五つあったのに。ストアは
内側からこれを検出できない。空のメモリとまったく同じに見える。

直接の MCP ハンドシェイクで `b4a` が健全だと分かったので、失敗は検索ではなく選択の
側にある。エージェントごとにメモリサーバーは一つ、あるいは選択が曖昧にならない名前を
付けること。MCP ツールをサーバー名で名前空間化するハーネス
（mcp__b4a__b4a_recall）はこれに当たらない。衝突には、似た名前のメモリツールを出す
二つのサーバーが必要だ。

## 最前線との比較

現在のエージェントメモリの風景の中で、これがどこに位置するかを率直に書く。強みだけを
並べた README は販売ページだからだ。

| 能力 | ここでの状態 |
|---|---|
| 構造化メモリ（型付き事実、選好、実体） | **部分的。** `kind` は自由形式のラベル、`tags` はスコープ、`refs` はリンク。スキーマも検証もない。kind が何を意味するかは呼び出し側が決める。 |
| 時間的・グラフ的メモリ（有効期間、関係の変化） | **未実装。** `created_at` はあり、`superseded_by` は置換を記録するが、有効区間もクエリ時のグラフ走査もない。グラフは作って測定したが、中国語コーパスで何も変わらなかった（D-024）。だから配線していない。`refs` が与えるのは一ホップの展開で、走査ではない。 |
| 衝突解決 | **実装済み、決定的。** `supersede(old, new)`。置き換えられた記憶は浮かび上がらなくなる。モデルは関与しない。PrecisionMemBench の supersession カテゴリ: 3/3。 |
| 書き込み経路の重複排除・パターン抽出 | **未実装。** 抽出（`remember()`）は存在するが**既定で無効**。書き込み時に測ると検索を損なうからだ（D-023）。 |
| 複数検索器の統合 | **未実装。** 検索器は一つ。バイグラムと、任意で jieba の語に対する BM25。 |
| 忘却・統合 | **粗い。** `prune(keep_sessions=N)` は新近性によるサイズ制御で、検索の改善ではない。ノイズの多いコーパスを回復するには 95% を削除する必要がある。忘却ではなく空にすることだ（D-022）。 |
| セッション横断の集約 | **未実装。** 今のところ明示的に範囲外。 |
| 能動的リコール | **部分的。** `recall-context` は標準入力からプロンプトを読み、整形した記憶を出力する。何も一致しなければ沈黙する。クライアント側のフックのために作った。MCP は pull 専用で、サーバーから記憶を差し出せないからだ。スケジューラはない。いつ実行するかはクライアントが決める。`integrations/hooks/` を参照。 |
| マルチモーダル | **未実装。** |
| ハルシネーション防御 | **部分的。** 証拠と判定の分離、`corpus_missing`、三状態のジャッジ結果。正しい検索から生まれた誤った回答を検出するものはない。 |
| 公開数値の再現性 | **強い。** ベンチマークは三つ、うち二つはモデルをループに入れていない。この軸でプロジェクトは分野の大半より先にいる。これは目標そのものではなく、モデルなし原則の帰結だ。 |

正直な要約: **これは異常なほど丁寧に測定された検索層であって、認知アーキテクチャ
ではない。** やることは一つ——正しい記憶を見つけ、何を見つけ、何を見つけなかったかを
明確に言う——残りは意図的に断る。その取引が正しいかは呼び出し側による。すでに
モデルを持つエージェントが欲しいのは証拠と明確な棄権シグナルであって、自分の記憶に
ついての第二のモデルの意見ではない。

## 現状

ライブラリ、CLI、MCP サーバーは完成している。メタデータ層——スコープタグ、置換リンク、
関係 refs、別索引テキスト——は最初のベンチマークを書いた後に導入した。

**意図的に作らず、予定もないもの:**

- **セッション横断の自動マージ。** 検索はすでにセッションをまたぐ。一つのクエリが
  保存済みの全セッションを検索し、最良のものを返す。未実装なのは複数セッションを
  一つの要約へ*統合する*ことだ。それにはモデルか、二つの記憶が同じものを指すと
  決める規則が要る。下手にマージすれば、読者が自分で量れたはずの細部が失われる。
- **マルチモーダル。** 範囲外。

**最近追加したもの:**

- **近似重複の検出。** 記憶ごとに SimHash フィンガープリントを持ち、二つの記憶が同じ
  ことを述べていそうなとき `duplicates_of(id)` が返す（検索経路では走らせない。
  全件走査は 2893 件で 5 ms、クエリ全体の半分以上にあたる）。報告するだけで
  マージしない。呼び出し側のエージェントが両方を読んで決める（D-028）。
- **weight（重み）。** `reinforce` が上げ、`decay` が下げ、`prune_by_weight` がしきい値を下回った
  ものを削除する。ここで初めて、年齢に関係しない忘却シグナルになった。検索された
  記憶は生き残り、されなかった記憶は減衰する（D-029）。

**最近直したもの:**

- **置き換えられた記憶が消えていた。** `supersede(old, new)` は古いほうを隠すが、新しい
  ほうが別の語を使うと——「main store is MySQL」を「migrated to PostgreSQL」で置き換える
  と——「main store」のクエリは隠されたほうだけに一致し、検索は何も返さなかった。
  更新された瞬間に事実を忘れる記憶システムは、最初から持たなかったものより悪い。
  ヒットは捨てずに現在の記憶へリダイレクトするようになった（D-027）。

**未実装、予定にあるもの:**

- **時間減衰による忘却。** `prune` は新近性によるサイズ制御で、D-022 はノイズの多い
  コーパスの回復に 95% の削除が必要だと測った。年齢ではなく重要度を重み付けする
  減衰が、次の本物の仕事だ。
- **リコールのスケジューラ。** `recall-context` はフック用にあるが、いつ実行するかを決める
  ものがない。毎ターンは安い（1.5 ms）が、おそらくノイズが多すぎる。
- **頻度ベースのランキング。** `accesses` は数えており、`weight` は `weight_blend` で
  ランキングに混ぜられるが、既定は無効。仕組みはテスト済みで、*役に立つか* は未測定だ。
  未測定のシグナルで結果の順序を変えるのは、このプロジェクトが断り続けてきた種類の
  変更である。
- **複数検索器の統合。** 今は BM25 が一つ。第二の語彙検索器はモデルなし原則を破らずに
  試せる。
- **`kind` のスキーマ。** 検証のない自由形式の文字列だ。

**測定して却下——先送りではなく、決定:**

- **クエリ時のグラフ走査。** 作り、中国語コーパスで測り、何も変わらなかった（D-024）。
  一ホップの `refs` 展開は効く——PrecisionMemBench で 4/4——が、それはリンクであって
  走査ではない。
- **書き込み時の抽出。** 検索を損なうので既定で無効（D-023）。

**モデルなしでは届かないもの:**

- **正しい検索から生まれた誤った回答の検出。** ここにあるシグナルはすべて、正しい
  記憶が返ったかどうかを語る。読者がそれをうまく使ったかは語らない。それには
  ジャッジが要り、間違うジャッジはないより悪い。

[決定ログ](docs/decisions.md) は 34 項目を両方向に記録している。検証して失敗した
仮説も含めて。[リサーチノート](docs/research.md) と
[ランドスケープ分析](docs/landscape.md) が周辺領域を扱う。

既知の限界はすべて測定済み。タグなしの検索は密な近似重複で劣化し（D-020）、クエリ側の
小細工では回復しない（D-021）。修正は書き込み時にある（D-025、D-026）。LoCoMo の
hit@1 は 0.6270 で、このデータセットで公開されている最高の回答精度には届かない。
そしてその差は読解ではなく検索だ。

## 設計上の決定

34 の決定が、それぞれ根拠となる測定か推論を伴って
[`docs/decisions.md`](docs/decisions.md) にある。両方向が記録されている。検証して
失敗した仮説も含めて。

## コントリビュート

検証ゲート:

```bash
python -m pytest tests/ -q
python -m ruff check src bench tests
python -m ruff format --check src bench tests
python -m bench.zh.e2e
python -m bench.pmb.run
python -m bench.locomo.run
```

`bench/zh/e2e.py` は出荷コード経路を実行し、`hit@1 0.9250` を報告するはずだ。
`bench.pmb.run` は `pass 64/77`、`bench.locomo.run` は `hit@1 0.6270` を報告するはずだ。
検索、トークン化、スコアリングの変更でいずれかが下がれば回帰だ。最後の二つは
API キーもネットワークも要らない。

設計上の決定を変えるときは、`docs/decisions.md` に新しい項目として、根拠となる測定を
添えて書く。
