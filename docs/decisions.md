## D-003 abstention 用 `_abs` 后缀识别，不看 `question_type`

**日期**：2026-11-06
**状态**：已执行（曾判断错误）

**问题**：怎么从数据里找出「无答案」题。

**我一开始判断错了**：以为这 500 题里没有 abstention 类型，因为按
`question_type` 统计只有 6 类，没有 abstention。据此写进了结论。

**实测推翻**：`question_id` 带 `_abs` 后缀的题有 **30 道**，分散在 4 个
`question_type` 里：

```
multi-session         12
single-session-user    6
temporal-reasoning     6
knowledge-update       6
```

**选择**：`is_abstention = question_id.endswith("_abs")`。

**教训**：`question_type` 是「问法」的分类，abstention 是「有没有答案」的属性，
两者正交。用一个字段去筛另一个维度，会静默漏掉整类样本——和这个项目要解决的
「静默失败」是同一种错误。

## D-005 中文用字符 bigram，不做词典分词

**日期**：2026-11-06
**状态**：待验证（当前无中文评测集）

**问题**：中文没有空格，怎么切词。

**选项**
1. jieba（词典 + HMM，~20MB 词典，纯 Python 慢）
2. 字符 bigram（无词典，O(n)）
3. 引入向量模型（重）

**理由支持 bigram**：
- 永远不会对汉字返回 0 个 token——这正是我们要避免的失败模式
- 无词典意味着没有「未登录词」问题，专有名词（`覆巢演出`、`角色管理页`）不会被切错
- 代价是索引膨胀（n 个字 → n-1 个 bigram）和精度损失

**已实现的降噪**：bigram 里含虚字占比过半就丢弃，但**不逐字符切分**。
`社会` / `会议` / `用户` 能活下来，`的了` / `是在` 被丢掉。
这个取舍来自 neural-memory 那一轮的教训：逐字符切停用字摧毁了 36/49 个常见词。

**待验证**：没有中文 benchmark，所以「bigram 够不够好」目前无法量化。
这是 D-006 的直接后果。

## D-007 检索本身不是瓶颈

**日期**：2026-11-06
**状态**：已实测

**问题**：一开始的假设是「检索是难点，所以要自建」。

**实测（BM25，零依赖，470 道可答题，排除 30 道 abstention）**

```
hit@1    0.866
hit@5    0.9511
hit@10   0.966
recall@10 0.9087
mrr      0.899
完全未命中  16 / 470
```

按类型：

| question_type | n | hit@10 | mrr |
|---|---|---|---|
| knowledge-update | 72 | 1.000 | 0.9769 |
| single-session-assistant | 56 | 1.000 | 1.0000 |
| single-session-user | 64 | 1.000 | 0.9701 |
| multi-session | 121 | 0.975 | 0.8973 |
| temporal-reasoning | 127 | 0.945 | 0.8786 |
| single-session-preference | 30 | 0.800 | 0.4656 |

**结论**：30 年前的算法 + 零依赖，在真实 haystack（平均 493 轮/题）上拿到 96.6%
hit@10。**「检索难」这个前提是错的。**

**这推翻了自建的一条主要理由。** 剩下 16 个未命中里，`single-session-preference`
（mrr 0.47）明显最弱——它要的不是「找到包含关键词的会话」，而是「推断用户偏好」。
那是理解问题，不是检索问题。

## D-008 分数不能当拒答信号

**日期**：2026-11-06
**状态**：已实测，假设否定

**问题**：如果检索器的 top-1 分数能区分「有答案」和「没答案」，拒答就可以用一个
阈值实现，Stage 1 会非常便宜。

**实测（BM25 top-1 原始分，500 题）**

```
abstention n=30   min= 9.61  median=19.67  max= 43.38
answerable n=470  min= 9.35  median=25.23  max=135.49
```

**两个分布几乎完全重叠。** abstention 题的分数能达到 43，比一半以上的正常题还高。

原因不神秘：每道 abstention 题都带一个诱饵——问仓鼠但只提过猫，问韩国但只提过
日本。诱饵和问题共享大量词汇，BM25 自然给高分。

阈值扫描（完整曲线在 `bench/results/abstention-probe.json`）：

| 阈值 | 拒答率 | 可答保留率 | 平衡 |
|---|---|---|---|
| 0 | 0.000 | 1.000 | 0.500 |
| 18 | 0.467 | 0.736 | 0.601 |
| **24** | **0.833** | **0.543** | **0.688** |
| 44 | 1.000 | 0.157 | 0.579 |

最佳平衡 **0.688**，随机基线是 0.5。而达到它的代价是**丢掉 46% 的正常查询**。

**结论**：用分数阈值做拒答不可行。这不是调参问题，是信号本身不存在。

**对 Stage 1 的直接影响**：拒答必须建模「问题与内容的关系」——这条记忆是否
**回答了**这个问题，而不只是**包含了**相关词。这是理解任务，不是排序任务。

**这是本次调研最有价值的产出。** Stage 1 的第一件事因此确定了，且有了量化的
靶子：在可答保留率 ≥0.95 的前提下把拒答率提上去。

## D-009 中文评测集：59 题，共享语料

**日期**：2026-11-06
**状态**：已建成

**问题**：8 篇论文的评测集全是英文，「中文优先」没有证据支撑。

**做法**：`bench/zh/build.py` 手写 30 个会话（127 轮）+ 59 道题（40 可答 / 19 abstention）。
内容取自真实 agent 工作记忆，不是机翻——机翻会保留英文句子结构，恰好抹掉要测的东西。

**关键设计：一份共享语料，不是每题一个 haystack。**
真实场景是一个 agent 一个项目库，所有问题搜同一批记忆。这更难，也更诚实。

**abstention 带诱饵**：每题问一个没提过的东西，但语料里提过相似的东西。
「问仓鼠但只提过猫」「问韩国但只提过日本」。问完全不相关的话题是白送的，
会flatter 任何阈值。

**人工核对发现的问题**：`zh048_abs` 问「全局预算多少秒」，而语料明确有「380 秒」——
这题其实可答，已从 abstention 移除。`zh041_abs` 是半可答的混合题，改成只问不可答的部分。
19 道 abstention 逐题看过 top-2 检索结果，确认答案确实不在语料里。

**加难度**：为 14 个会话生成实体替换的硬负样本（`s01v` 等），语料从 30 涨到 44 会话。
同一话题、不同事实——真实记忆库里就有三个项目都有媒体投稿页。

**局限**：44 会话仍然太小，hit@10 饱和在 1.0。**hit@1 (0.825) 才是当前有区分度的指标。**

## D-010 D-005 验证：bigram 够用，但 jieba 更准

**日期**：2026-11-06
**状态**：D-005 部分成立

**实测（中文集 59 题，同一 BM25）**

| 指标 | bigram | jieba |
|---|---|---|
| hit@1 | 0.825 | **0.875** |
| hit@5 | 0.950 | 0.950 |
| hit@10 | **1.000** | 0.975 |
| MRR | 0.8911 | **0.9098** |
| 未命中 | **0** | 1 |

**结论**：jieba 精确度略高（hit@1 +5pp，MRR +0.02），但召回更低——
未登录词会被切错，bigram 不会。两者对拒答都没有帮助（0.696 vs 0.695）。

**保留 bigram 作为默认**：召回不输、零依赖、专有名词不会切错（`覆巢演出`、`角色管理页`）。
jieba 只在 `bench/zh/compare_tokenizers.py` 里作为测量工具。

**被否定的假设**：原以为词典分词能改善拒答信号。实测不能——拒答瓶颈不在分词。

## D-011 拒答：记忆系统只给证据，判断交给调用方

**日期**：2026-11-06
**状态**：已定架构

**问题**：D-008 证明分数不能当拒答信号。那能不能用本地 LLM 判断？

**试过，能，但不该做。**

用本地模型问「这段证据里有没有回答问题所需的信息」，在中文集 59 题上：

```
Stage 0（总是回答）    keep 1.000   refuse 0.000
带模型判断             keep 0.950   refuse 0.895   ← 目标达成
```

**代价**：`qwen3.5:9b` 常驻 15.2 GB。这台机器总共 23.6 GB，实测跑到一半整机卡死。
`qwen3.5:4b` 要 9 GB，只能到 keep 0.92。`2b` 只要 1 GB，但 keep 只有 0.75。

**为什么放弃这个方案**（不只是因为内存）

调用方本来就是 agent，它自己就有模型。让记忆系统再起一个模型来问「这条记忆相关吗」，
是重复开销，不是功能。而且它把记忆系统从「几十 MB 的库」变成「要 15 GB 的服务」——
这不是一个记忆库该有的形态。

顺带核实过：neural-memory 也用了 sentence-transformers 和 spacy，
但它们全在 `optional-dependencies` 里，**核心路径不需要模型**。这一点是对的，应该照做。

**最终架构**

```
记忆系统                              调用方（agent）
─────────                            ──────────────
检索 → 排序                           拿到 evidence + missing_terms
每条带：score / coverage / 缺失词      用自己已有的模型判断要不要信
零模型、零推理、几十 MB                或者直接把缺失词展示给用户
```

`bench/zh/evidence.py` 就返回这个。`missing_terms` 是关键字段——不是分数，是**具体的词**：

```
可答：杭州测试机的地址和部署目录是什么？  cov=1.00  无缺失
不可答：杭州测试机上装的是什么数据库？    cov=0.44  缺失 ['数据库']
```

调用方看到 `缺失 数据库` 就能判断，不需要任何额外的模型调用。

**非模型方法的上限，全部实测过**

| 信号 | keep≥0.95 时的拒答率 |
|---|---|
| BM25 top-1 分数 | ~0 |
| IDF 加权覆盖 | ~0 |
| 未见词占比（bigram） | ~0.05 |
| 未见词占比（jieba） | 0.105 |
| 词级 coverage | ~0.10 |
| **本地 LLM 判断** | **0.895** |

差一个数量级。所以：**拒答不是记忆系统的能力，是调用方基于证据做的决策。**
记忆系统的责任是把证据做干净，不是替调用方下结论。

**这个决定放弃的东西**：开箱即用的拒答。代价由调用方承担，但那是本来就该承担的一方。

**分词的选择顺带定了**：`missing_terms` 需要真正的词，不是 bigram。
`数据库` 被切成 `数据`+`据库` 后，`数据` 在语料里出现过，信号就没了。
所以词级提取用 jieba（20 MB 词典，不是模型，无推理开销），**检索仍走 bigram**——
那里 bigram 的召回优势还在。jieba 缺失时回退到 bigram，报告变糙但仍然正确。

## D-012 QPP 与分类器：都试过，都不够

**日期**：2026-11-07
**状态**：已实测，两条路都封死

**问题**：D-011 说拒答交给调用方。但在交出去之前，零模型到底能到什么程度？
信息检索有一个专门研究这个的子领域（Query Performance Prediction），
经典方法全是纯统计，理论上正合需要。

**实测（中文集 59 题，keep≥0.95 时的拒答率）**

| 方法 | 拒答率 | 出处 |
|---|---|---|
| NQC（归一化查询承诺） | 0.158 | Shtok et al. 2012 |
| UQC | 0.158 | 同上 |
| WIG（加权信息增益） | 0.000 | Zhou & Croft 2007 |
| Clarity | 0.105 | Cronen-Townsend et al. 2002 |
| top1 − top10 分差 | 0.105 | 自建 |
| 13 特征 + 逻辑回归 + LOOCV | **0.211** | 自建 |
| 本地 LLM | 0.895 | D-011 |

**文献也预期会失败。** arXiv:2504.01101（Chifu 等，2025）跨四个集合、四种检索器
测了 QPP，结论：预测器与真实性能相关性不高、对集合敏感、
「selective query processing offers only marginal gains」。

**根因**：QPP 预测的是**排序质量**，不是**答案是否存在**。
一个查询可以完美检到最相关的会话，而那个会话里没有答案——
abstention 题正是这么设计的。这是问的东西和答的东西不是一回事。

**分类器组合为什么也不行**：13 个特征组合后到 0.211，是单特征的两倍，
但仍只有 LLM 的四分之一。特征权重里最有意义的 `t_howmany`（问「多少/几次」）+0.859：
问具体数值的更容易无答案。但「数据库」和「部署目录」是不是同一概念，
需要语义理解，统计做不到。

**结论**：零模型拒答上限 **0.211**。这个能力做进系统，
标为「尽力而为」，不作为可以依赖的保证。真正的判断交给调用方。

## D-013 竞品：这个领域已经很卷，空白在「中文 + 零模型 + 单文件」

**日期**：2026-11-07
**状态**：已调研

详见 `docs/landscape.md`。要点：

- **腾讯 TencentDB-Agent-Memory**：30,584 stars，TypeScript，MIT。
  团队级记忆中枢，四类资产（Chat Memory / Skill / LLM-Wiki / Code-Graph）。
  **安装第一步就是填两组 LLM 参数**——强制依赖模型。
- **causal-memory**：104 stars，Rust，Apache-2.0，368 个测试，2026-11 仍在更新。
  因果边 + 抑制性扩散激活 + SWR 巩固 + CausalEval 基准。
  **用本地 ONNX embedding**——不是 LLM，但仍是模型。
  自述「事实召回不是我们的强项」（LongMemEval-S 76.4% vs mem0 94.4%）。
- mem0 / Zep / Letta / Cognee：全部依赖 embedding 或 LLM。

**空白**：没有项目同时满足「中文原生 + 零模型 + 单文件 SQLite」。
腾讯面向中文但强制 LLM，causal-memory 零外部 API 但只做英文，mem0 需要向量库。

**决定**
1. 不重复做因果模型——causal-memory 已经做了 368 个测试，再做一个不如用它。
2. 定位收窄到「中文 + 零模型 + 单文件」。
3. 借鉴但不照抄：它的写入分流（raw 进审计表，distill 出事实和因果边）值得抄。

**诚实的保留**：这是技术空白，不是验证过的需求。
愿意为「不用模型」付准确率代价的用户有多少，不知道。

## D-014 云端 API：可行，延迟 0.8s，但不解决高频场景的体验

**日期**：2026-11-07
**状态**：已实测

**问题**：本地模型要么卡机器（9b/15GB），要么不准（2b/keep 0.75）。
云端 API 能不能绕开这个两难？

**实测（`deepseek-flash`，中文集 59 题，带一次重试）**

```
keep_rate    0.925      （需要 0.95，差 1 题）
refuse_rate  1.000
errors       0 / 109 次调用
延迟         均值 0.807s  中位 ~0.6s  最大 1.611s
tokens       213.8 / 次
```

**和本地对比**

| 方案 | keep | refuse | 单次延迟 | 常驻内存 |
|---|---|---|---|---|
| 纯 BM25 | 1.000 | 0.000 | 0.22 ms | 0 |
| 本地 2b | 0.750 | 1.000 | 0.77 s | ~1 GB |
| 本地 9b | 0.950 | 0.895 | 1.5–2 s | **15.2 GB** |
| **云端 deepseek-flash** | **0.925** | **1.000** | **0.81 s** | **0** |

云端用零内存换到了接近 9b 的准确率。这是它唯一但很实在的优势。

**踩到的坑**

1. `deepseek-chat` 全程 HTTP 503「Service is too busy」；`deepseek-flash` 能用。
2. `deepseek-flash` 是 reasoning 模型，会先输出 `reasoning_content`。
   `max_tokens=8` 时思考把预算吃光，`content` 返回空字符串——看起来像模型没回答，
   实际是预算不足。要留 256。
3. 无重试时失败率约 5–6%（500 / 503 / 返回 `null` body）。
   加一次重试后 109 次调用 0 失败。**重试是必须的，不是优化。**
4. 偶发极端延迟：无超时保护的一次跑出现过 363 秒。现在超时设 30 秒，
   超时当作「无判断」，不当作「无答案」。

**为什么这仍然不是高频场景的答案**

0.81 秒 × 一个任务 30 次记忆查询 = **24 秒**额外延迟。
可感知，不致命，但和「零模型 0.22 毫秒」是两个世界。

真正的问题是：这个判断本可以不做。调用方的 agent 正在推理，
它顺手就能判断「这条记忆相不相关」。为它单独发起一次 API 调用，
是串行化的第二次推理。

**成本反而不是问题**：214 token/次，按 DeepSeek 定价约 0.0001 元/次，
每天一千次查询一毛钱。

**结论**

- 云端方案可以作为**可选增强**存在：默认零模型，配置了 key 才启用。
- 启用后延迟 0.8s，需要缓存 + 短超时 + 重试三件套才稳。
- 高频路径上，仍然推荐把判断交给调用方。

## D-016 集成云端 judge：三态，不是两态

**背景**

D-014 确认云端 judge 可行但慢。要不要接进系统、怎么接。

**决定**

接，但三个约束：

1. **默认关**。Judge.from_env() 读 BRAIN4AGENT_JUDGE_KEY，没配返回 None。
   核心路径 store.search() 永远不碰网络。
2. **三态**。search_judged() 返回 ound / 
ot_found / uncertain。
3. **重试与超时写死在 Judge 里**。默认 30 秒、重试 1 次——不是可调参数，
   是 D-014 实测出来的必需品。

**为什么第三态是必须的**

两态设计里，judge 挂掉只能归到 
ot_found。于是网络故障期间，
系统会对用户说「我从来没记过这件事」——而它其实不知道。

这是本项目要修的 bug 的高级版本：不是返回空列表，而是返回一个自信的错误结论。

**实现上的一个坑**

max_checks 限制最多问几个会话。每次判断是一次 API 调用，
不加限制会在检索结果多时线性放大成本。

**已知差距**

keep 0.925，低于本地 9b 的 0.950。差的那 1 题没分析——
可能是模型判断问题，也可能是数据问题（zh012 的答案与问题字符重合 43%）。
这个差距不影响「可选增强」的定位，但影响「默认开启」是否合理。

## D-017 MCP 用标准库实现，不装官方 SDK

**问题**

要成为 agent 真正能用的东西，得有 MCP 接口。官方 mcp 包带一百多个间接依赖。

**权衡**

stdio transport 只需要四个方法：initialize、	ools/list、	ools/call、ping，
外加「通知不回复」这一条规则。线格式是换行分隔的 JSON-RPC 2.0。

官方 SDK 提供 schema 校验、类型提示、多种 transport、OAuth。都有用，
但都不是「让 agent 读一条记忆」所需要的。

**决定**

自己写。mcp 不进 dependencies。

**代价，说清楚**

1. 协议版本要自己跟。现在锁 2024-11-05，出新版要手动适配。
2. 没有 schema 校验，工具参数靠手写检查。
3. 只支持 stdio，没有 SSE / HTTP。

**如果以后需要 HTTP transport**，那时再引入 SDK 是对的——那部分不是四个 dict。

**必须守住的一条**

stdout 只能有协议消息。任何一个 print 都会破坏流，客户端看到的是 parse error
而不是工具结果。所有日志走 stderr。测试里有一条端到端用例，跑真实进程，
逐行 json.loads 验证。

## D-018 missing_terms 的正确语义：语料缺失，不是会话缺失

**问题**

D-011 提出把「问题里的词语料没有」当作零模型信号。实测 top-1 的 keep 只有
**0.325** —— 40 道可答题里 27 道被误拒，完全不可用。

**两个错误，分开看**

**其一：没有过滤词性。** 直接、应该、不是、哪几个、最终、需要、修复
是提问的语法，不是答案的内容。它们在语料里缺失是正常的。
加上 jieba 词性过滤，只保留名词性词（n / nr / ns / nt / nz / eng / vn / an，
外加长度三以上的数字串如 IP 和版本号）后，假拒答 27 → 16。

顺带发现 jieba 把 一共 标成 j（简称略语），所以 j 从白名单里去掉 ——
标注不可靠的标签不如不要。

**其二：语义搞错了，而且这个错误更大。** 我在问「这个词在**这个会话**里有没有」。
但 用户、记忆、媒体、问题 在多数单个会话里没有，在整个语料里有。
16 个假拒答里有 10 个是这一类。

正确的问题是：**这个词在整份语料里有没有**。

- 会话缺一个词 → 只说明这次检索不相关，是排序问题
- 语料缺一个词 → 才是「我不知道这个东西」

现在两个都暴露，但名字分开：

- SearchResult.corpus_missing — 整份语料都没有（强信号，事实）
- Evidence.missing_terms — 这个会话没有（解释它为什么排在这里）

**修正后**

`
                 keep    refuse
总是回答         1.000   0.000
missing_terms    0.875   0.632     <- 零模型
本地 9b          0.950   0.895
云端 flash       0.925   1.000
`

**和 D-012 的关系**

D-012 测的所有信号在 keep 0.95 时拒答率最高 21%。missing_terms 在 keep 0.875
时到 0.632。不是同一个价位：keep 低 7.5 个点，换来拒答率高三倍。

但它不是「更好」，是**不同种类**：它给出的是一个事实（语料里没有这个词），
不是信心分数。调用方拿到的是可以展示、可以推理的东西，不是 0.31。

**仍然不做二值判断**

keep 0.875 意味着 12.5% 的可答题会被误拒。作为自动拒答不够好，
所以继续只当证据交给调用方。

**剩下的 5 个假拒答**

组件、核心、水平、态度、调整，都是真名词，语料里确实没有。
不修了：这些词在别的语境里可能就是关键实体，为一个 59 题的集合去调停用词表，
只会让它在这 59 题上好看。

**验证方式**

python -m bench.zh.missing_terms_signal 可复跑。同时 ench/zh/e2e.py 用产品代码
跑同一套语料，检索指标与 D-010 基线逐位一致 —— 语义改动没有动到排序。
